# Database schema — LFCA exam simulator

**Status:** approved, Phase 4, 2026-08-30
**Postgres 18 (Neon), accessed through Drizzle.** This is the spec `app/src/db/schema.ts` implements.
*Measured 2026-08-31 against the provisioned project: Neon served **18.6**, not the 16 this document
assumed at planning time. §0 records what that changes.*
Architecture: [03-technical-design.md](03-technical-design.md) · API: [07-api-design.md](07-api-design.md)

---

## 0. Conventions

- **snake_case** columns, **singular** table names (`answer`, not `answers`) — Drizzle's generated
  types then read as one row, which is what they are.
- **`created_at timestamptz NOT NULL DEFAULT now()`** on every table. **`updated_at`** only where a
  row is actually mutated after insert: `user`, `attempt`, `answer`. Content tables have no
  `updated_at` — they are replaced wholesale by the seed, never edited.
- All timestamps are **`timestamptz`**, always UTC. A 90-minute clock that drifts on a DST boundary
  is a bug this rules out at the type level.
- Content-table primary keys are the **bank's own string ids** (`q.linux.command-line.awk.03`).
  User-data primary keys are **UUIDv7** — sortable by creation time, which makes `ORDER BY id`
  meaningful for attempt history without a second index.
  **Generated by the database, not the application.** Postgres 18 ships `uuidv7()` in `pg_catalog`
  (verified on the provisioned branch: two overloads, `uuidv7()` and `uuidv7(shift interval)`), so
  `attempt.id` takes `DEFAULT uuidv7()` and needs neither an extension nor an application-side id
  generator. On the Postgres 16 this document originally assumed, it would have needed one of those,
  and the id would have been minted somewhere `src/domain/` could not see. Prefer the default: an id
  that the database assigns cannot be assigned twice by two racing callers.
- `text` everywhere over `varchar(n)`. There is no length limit worth enforcing at the database that
  the Zod schema at the boundary does not enforce better.
- The two halves of this schema have different rules: **content tables are read-only to the
  application** and rewritten only by `npm run seed`; **user tables are never touched by the seed.**

## 2. Auth tables (Better Auth — generated, not designed here)

Generated by `npm run auth:generate` in `app/`, which runs Better Auth's own CLI. **The package is
`auth`, not `@better-auth/cli`** — the latter was renamed and is now marked deprecated on npm; the
`auth` package is published from the same repository by the same maintainer, at a version locked to
`better-auth`. *Generated as shipped, against better-auth 1.7.2 on 2026-08-31:*

- **`user`** — `id` (text, pk), `name`, `email` (unique), `email_verified` (bool),
  `image` (text, null), `created_at`, `updated_at`, **`allowlisted`** (bool, default false).
- **`session`** — `id` (text, pk), `user_id` → `user.id` **on delete cascade**, `token` (unique),
  `expires_at`, `ip_address` (null), `user_agent` (null), `created_at`, `updated_at`.
- **`account`** — `id` (text, pk), `user_id` → `user.id` **cascade**, **`issuer`**, `provider_id`,
  `account_id` (the Google `sub`), `access_token`, `refresh_token`, `id_token`,
  `access_token_expires_at`, **`refresh_token_expires_at`**, `scope`, **`password`** (unused —
  present whether or not email/password is enabled), `created_at`, `updated_at`. Unique on
  `(issuer, account_id)`.
- **`verification`** — `id` (text, pk), `identifier`, `value`, `expires_at`, timestamps.

**Two divergences from what this document assumed, both the library's to decide (§0's rule that the
auth tables' columns are not ours):**

1. `issuer`, `refresh_token_expires_at` and `password` were not anticipated here. They are harmless;
   `password` stays null because no credential provider is configured.
2. **The auth tables' timestamps are `timestamp`, not `timestamptz`** — the generator emits them
   without a time zone, which is the one place §0's "all timestamps are `timestamptz`" does not
   hold. Our own tables are all `timestamptz`. Neon and Vercel both run UTC, so the practical risk is
   a session expiry computed against a non-UTC server clock, which does not exist in this
   deployment. Recorded rather than patched: editing the generated file would be reverted by the
   next regeneration.

**One addition of our own, `allowlisted`** — declared as a Better Auth `user.additionalFields` entry
in `app/src/auth.ts`, so the generator emits it, rather than bolted on by a later `ALTER TABLE` as
this document originally specified. The `ALTER` would have worked exactly once: the next
regeneration would drop the column from the Drizzle definition and the following
`drizzle-kit generate` would write a migration deleting it — from the table holding the flag that
decides who may sign in. See the decision log, 2026-08-31.

Set true at the OAuth callback when the email is in `ALLOWED_EMAILS` (doc 08). Every app query joins
on it. It is defence in depth behind the callback check, not a replacement for it — the callback is
what stops the row being created at all.

`user.id` is **text**, not uuid, because Better Auth generates it. Every `user_id` foreign key in
§5 matches that type.

## 3. Content tables

### 3.1 `question`

One row per item in `questions/**/*.json`. Measured against the bank on 2026-08-30: **1,150 rows,
every one with exactly four options, none missing `why` text.**

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | text | no | — | **PK.** The bank's id, e.g. `q.security.compliance.policy-standard-and-procedure.02`. |
| `concept_id` | text | no | — | e.g. `linux.command-line.command-syntax`. Not a foreign key — concepts live in `data/topics/` and are not seeded. |
| `competency` | text | no | — | e.g. `Linux Fundamentals :: Command Line`. 22 distinct values. |
| `domain` | `domain` enum | no | — | `linux \| sysadmin \| cloud \| security \| devops \| pm`. Derived by the seed from the id's second segment; the seed **fails** on an unrecognised segment rather than defaulting. |
| `pool` | `pool` enum | no | — | `exam \| supplement`. 1,000 exam / 150 supplement. |
| `type` | `question_type` enum | no | — | `application \| discrimination \| diagnostic \| command \| recall`. |
| `difficulty` | smallint | no | — | 1–5, `CHECK (difficulty BETWEEN 1 AND 5)`. |
| `stem` | text | no | — | Markdown-ish; contains backticked code. Rendered as text with inline code, never as raw HTML. |
| `is_holdout` | boolean | no | `false` | True for exactly the 40 ids in `data/holdout.json`. **The seed asserts the count is 40 and aborts the transaction otherwise.** |
| `created_at` | timestamptz | no | `now()` | Seed run time. Not meaningful; present for uniformity. |

**Indexes**

| Index | Justifies |
| --- | --- |
| pk on `id` | Every answer join and every review render. |
| `idx_question_selection` on `(domain, is_holdout, pool)` | The selection query in practice and domain mode: `WHERE domain = $1 AND is_holdout = false AND pool = 'exam'`. This is the only hot query in the app that is not a primary-key lookup. |

At 1,150 rows Postgres will often sequential-scan this anyway. The index is cheap, and it documents
the query that matters.

### 3.2 `question_option`

**4,600 rows** — exactly four per question.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `question_id` | text | no | — | → `question.id` **ON DELETE CASCADE**. Cascade is right here: options have no meaning without their question, and the seed's truncate-and-reinsert relies on it. |
| `ref` | text | no | — | `o1`–`o4`, the bank's own option reference. |
| `position` | smallint | no | — | 0–3, the option's index in **authored** order. Practice and domain mode render by this. Exam mode re-orders per doc 03 §3.2. |
| `text` | text | no | — | The option text. |
| `correct` | boolean | no | — | Exactly one true per question — **asserted by the seed**, not merely expected. |
| `why` | text | no | — | The explanation. Non-null: measured, zero options in the bank lack it. If that ever changes, `npm run validate` fails before the seed runs (PRD §5). |
| `provenance_kind` | text | no | — | `key \| sibling \| misconception \| variant \| confusable`. Not rendered in v1; seeded because dropping authored provenance at the database boundary is how it stops being maintained. |
| `provenance_concept_id` | text | yes | `null` | Present on `sibling` and some others. |

**PK:** composite `(question_id, ref)`.
**Index:** the PK covers every access. Options are only ever fetched by question.

### 3.3 `exam`

**16 rows.**

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | text | no | **PK.** `exam-01` … `exam-16`, from `exams/index.json`. |
| `number` | smallint | no | 1–16, for ordering the list on E6 without parsing the id. |
| `question_count` | smallint | no | 60 for all sixteen, stored rather than assumed. |
| `created_at` | timestamptz | no | Seed run time. |

### 3.4 `exam_item`

**960 rows** — 16 × 60, and measured to be 960 *distinct* questions with zero overlap between papers.

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `exam_id` | text | no | → `exam.id` **ON DELETE CASCADE**. |
| `seq` | smallint | no | 0–59. The question's position on the paper — PRD E1's "defined order". |
| `question_id` | text | no | → `question.id` **ON DELETE RESTRICT**. Restrict, not cascade: a question that an exam uses must never be deletable without the deleter confronting it. |
| `correct_position` | smallint | no | 0–3, from `index.json`. Where the correct option sits on the generated paper. See doc 03 §3.2 for how it drives rendering. |

**PK:** composite `(exam_id, seq)`.
**Unique:** `(exam_id, question_id)` — a paper cannot ask the same question twice.
**Index:** `idx_exam_item_question` on `question_id`, justifying "which exam is this question on?" on
the review screen and, more importantly, the holdout integrity check.

## 5. User-data tables

### 5.1 `attempt`

One sitting in any mode. The `mode` column discriminates; exam-only columns are nullable and their
consistency is enforced by check constraints rather than convention.

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `id` | uuid | no | `uuidv7()` | **PK.** Assigned by Postgres (§0), never by the app. |
| `user_id` | text | no | — | → `user.id` **ON DELETE CASCADE**. Deleting the account deletes the history; there is no other owner it could belong to. |
| `mode` | `attempt_mode` enum | no | — | `exam \| practice \| domain \| holdout`. |
| `exam_id` | text | yes | `null` | → `exam.id` **ON DELETE RESTRICT**. Non-null exactly when `mode = 'exam'`. Restrict: a seed that dropped an exam with attempts against it must fail loudly. |
| `domain` | `domain` enum | yes | `null` | Non-null exactly when `mode = 'domain'`. |
| `question_count` | smallint | no | — | 60 / 60 / 20·40·N / 40. Frozen at start — a later selector change never rewrites a past sitting. |
| `started_at` | timestamptz | no | `now()` | **The clock's only authority** (doc 03 §6). Never updated. |
| `time_limit_seconds` | integer | yes | `null` | 5400 for `exam`, 3600 for `holdout`, `null` for `practice` and `domain`. Null means no clock and no expiry, ever. |
| `submitted_at` | timestamptz | yes | `null` | Null while in progress. Set exactly once, by a conditional update (doc 03 §11). |
| `submit_reason` | `submit_reason` enum | yes | `null` | `user \| expired`. Non-null exactly when `submitted_at` is. Distinguishes "I finished" from "the clock ran out while I was away", which E6 must not conflate. |
| `score` | smallint | yes | `null` | Correct-answer count. Set at submit, for scored modes only. |
| `is_first_attempt` | boolean | no | `false` | True on the earliest attempt at a given `(user_id, exam_id)`. **Set at start, never rewritten** (§5.2). Meaningless and always false outside `mode = 'exam'`. |
| `created_at` / `updated_at` | timestamptz | no | `now()` | |

**Check constraints — these are the schema, not decoration:**

```sql
CHECK ((mode = 'exam')   = (exam_id IS NOT NULL))
CHECK ((mode = 'domain') = (domain  IS NOT NULL))
CHECK ((mode IN ('exam','holdout')) = (time_limit_seconds IS NOT NULL))
CHECK ((submitted_at IS NULL) = (submit_reason IS NULL))
CHECK (score IS NULL OR mode IN ('exam','holdout'))
CHECK (score IS NULL OR score BETWEEN 0 AND question_count)
```

**Indexes**

| Index | Justifies |
| --- | --- |
| pk on `id` | Every request during a sitting. |
| `idx_attempt_user_exam` on `(user_id, exam_id, submitted_at DESC)` | E6's exam list: best score, first-attempt score and attempt count for all sixteen, in one pass. |
| `idx_attempt_open` on `(user_id, submitted_at)` **WHERE `submitted_at IS NULL`** | "Do I have an attempt in progress?" — asked on every home-screen render. Partial index; at most a handful of rows ever qualify. |

**One unique index, and it earns its place:**

```sql
CREATE UNIQUE INDEX one_first_attempt_per_exam
  ON attempt (user_id, exam_id)
  WHERE is_first_attempt;
```

PRD §5 requires the first-attempt flag to be set exactly once per exam. §5.2 explains when it is
set and why; this index is what makes a race a database error instead of a silently corrupted honest
number — the one number in this product that cannot be regenerated.

### 5.2 When `is_first_attempt` is set — at start, not at submit

**At `INSERT`, when the attempt is created:**

```sql
INSERT INTO attempt (user_id, mode, exam_id, question_count, started_at, time_limit_seconds,
                     is_first_attempt)
SELECT $user, 'exam', $exam, 60, now(), 5400,
       NOT EXISTS (SELECT 1 FROM attempt WHERE user_id = $user AND exam_id = $exam)
RETURNING id;
```

Setting it at submit is wrong, and the failure is not hypothetical: start exam 07, abandon it, start
it again the next day, and finish the second sitting first. At submit-time the *second* attempt would
claim the flag — while the abandoned one, once its 90 minutes lapse, is finalised later and cannot.
PRD §5 says the opposite: an abandoned attempt **is** the first attempt. Setting the flag at start
makes it a property of *being earliest*, which is what it means, and makes it independent of the
order in which sittings happen to be finalised.

**Race:** two simultaneous starts both read `NOT EXISTS` as true; the second `INSERT` violates
`one_first_attempt_per_exam` and is retried once with the flag false. A unique-violation retry is
correct here precisely because the loser genuinely is not first.

### 5.3 `answer`

One row per question answered within one attempt. Written immediately on click, upserted so retries
are safe (doc 03 §7).

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `attempt_id` | uuid | no | — | → `attempt.id` **ON DELETE CASCADE**. |
| `question_id` | text | no | — | → `question.id` **ON DELETE RESTRICT**. This is the constraint that makes renaming a bank id a loud failure rather than orphaned history (doc 03 §3). |
| `option_ref` | text | yes | `null` | The chosen option. Null means seen-and-flagged-but-unanswered. |
| `is_correct` | boolean | yes | `null` | **Denormalised on write** by looking up `question_option.correct`. Null when `option_ref` is null. Stored rather than joined so that a future bank correction cannot silently rewrite a past score — the sitting records what was true when it was sat. |
| `flagged` | boolean | no | `false` | Exam mode only (E2). Persisted like an answer, not held in the browser. |
| `answered_at` | timestamptz | yes | `null` | Set on first non-null `option_ref`; **not** advanced by a later change. This is what "least-recently-seen" reads (PRD P3). |
| `created_at` / `updated_at` | timestamptz | no | `now()` | `updated_at` moves on every change of answer or flag. |

**PK:** composite `(attempt_id, question_id)` — this *is* the upsert key from doc 03 §7. There is no
surrogate id; a second answer to the same question in the same sitting is not a thing that exists.

**Foreign key:** `(attempt_id, question_id)` is additionally validated in application code against
the attempt's own question set (doc 03 §9) — the database cannot express "must be one of the 60 this
attempt asked" without a third table, and a third table is not worth it for one user.

**Indexes**

| Index | Justifies |
| --- | --- |
| pk on `(attempt_id, question_id)` | The upsert, and the review screen's full read. |
| `idx_answer_seen` on `(question_id, answered_at DESC)` | Unseen-first selection (P3): "which of this domain's questions has this user answered, and when last?" — joined to `attempt` on `user_id`. |

**Selection query this schema is shaped for** (practice/domain, per domain quota):

```sql
SELECT q.id
FROM question q
LEFT JOIN LATERAL (
  SELECT max(a.answered_at) AS last_seen
  FROM answer a JOIN attempt t ON t.id = a.attempt_id
  WHERE a.question_id = q.id AND t.user_id = $user
) s ON true
WHERE q.domain = $domain AND q.pool = 'exam' AND q.is_holdout = false
ORDER BY s.last_seen ASC NULLS FIRST, random()
LIMIT $quota;
```

`NULLS FIRST` is the whole of "unseen before seen". `random()` breaks ties so repeated sessions do
not serve an identical set. `is_holdout = false` appears here as well as in the seed and the
validator — three independent places, per doc 03 §11.

## 7. Deletion, retention and expiry

| Data | Rule |
| --- | --- |
| `attempt` and `answer` | **Never deleted by the app.** There is no delete endpoint, no "clear history", no soft-delete column — because there is nothing to soft-delete *from*. An abandoned attempt is kept and auto-submitted precisely so the honest number cannot be dodged (PRD §5). |
| `user` | Deleted only by hand, in SQL, and it cascades to sessions, accounts, attempts and answers. Deliberately not a feature: an accidental account deletion destroys the first-attempt scores, which are the one irreplaceable thing here (doc 03 §9). |
| `session` | Expires at `expires_at` (30 days). Better Auth cleans up; expired rows are harmless. |
| `verification` | Short-lived, cleaned by Better Auth. |
| Content tables | Replaced wholesale on every `npm run seed`, inside one transaction. |
| OAuth tokens on `account` | Kept while the account exists. Excluded from logs and Sentry (doc 03 §9). |

**Nothing expires on a schedule and there is no cron.** The only time-based behaviour in the system
is the derived clock (doc 03 §6), which is evaluated lazily on read.

## 8. Migrations

`drizzle-kit generate` produces a numbered SQL file in `app/src/db/migrations/`; `drizzle-kit
migrate` applies it. Migrations are **committed and reviewed as SQL**, never applied from a
`push`-style sync — the schema is not something to discover after the fact when it holds the only
copy of the first-attempt scores.

CI runs migrations against a Neon **preview branch** before production (doc 12). The order on deploy
is: migrate, then seed, then release. A migration that fails leaves the previous release serving.
